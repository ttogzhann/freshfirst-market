### Preserved r1 text

1. **AC-01 — Responsive navigation (TC-01): YES** only if, in the recorded browser, the five destinations (Dashboard, Pantry, Recipes, Basket, Shopping List) are reachable and the active destination is apparent at **1280×800 desktop** and **375×812 narrow**. At 375px the menu opens, each destination navigates, and it closes after navigation; no navigation or core control is clipped or requires horizontal page scrolling. With keyboard only, Tab/Shift+Tab reaches the menu toggle and links, Enter/Space activates them, and focus remains visible. Record browser/version, OS, actual viewport and any exception.
2. **AC-02 — Pantry form and feedback (TC-02): YES** only if add/edit accepts a catalog ingredient, positive quantity/unit and valid expiry date, saves and displays the resulting item, and the saved item remains after refresh. Submit invalid quantity/date and one controlled service error; an actionable error is visible, entered values remain available to correct/retry, and no false success or unintended mutation occurs. Check form visibility/operation at both viewports and keyboard submission/cancel.
3. **AC-03 — Batch controls and saved selection (TC-03): YES** only if a recipe’s whole-batch quantity can be changed at boundary values 1 and 8, the displayed ingredient amounts follow the selected batch count, and the selected count/substitutions remain when the selection is reopened from Basket. Check detail and basket controls at both viewports and keyboard operation; do not reinterpret batches as people/servings.
4. **AC-04 — Shopping, overwrite and purchase confirmation (TC-04): YES** only if list generation and manual quantity editing are usable at both viewports; regenerating edited/purchased generated lines presents the overwrite choice; **Cancel** leaves those edits intact and **Confirm** performs the stated regeneration (preserving manual lines unless reset was selected). A purchased catalog item requires actual quantity and expiry date before transfer; invalid values show actionable errors without transfer, and transfer succeeds only after explicit confirmation. Check keyboard access to both confirmation choices and error recovery.
5. **AC-05 — Cooking confirmation/cancel/error (TC-05): YES** only if the cook preview is readable at both viewports, **Cancel** leaves pantry/history unchanged, a valid **Confirm & deduct** updates pantry and recent history once, and an insufficient-stock/stale-stock failure blocks deduction and communicates recovery without false success or automatic retry. Verify keyboard operation of the dialog and choices.
6. **AC-06 — Long report content (TC-06): YES** only if a naturally available multi-entry import report can be read through its final entry at 375px and desktop, and the report can still be closed (including Escape) with focus returned sensibly. Record if the environment cannot produce a sufficiently long report; that criterion is **unverified**, not passed. Do not fabricate production/source content to create evidence.

For every TC, record observed YES/NO (or unverified), concise steps/result, browser+version, OS, viewport, and sanitized evidence. **These are implementation capabilities already present versus required evidence:** app routes/forms/dialogs are existing implementation; FF-46 supplies the independent browser/keyboard evidence only. A reproduced functional failure is an MVP blocker to report/escalate, not grounds to weaken a criterion or move it to Post-MVP.
